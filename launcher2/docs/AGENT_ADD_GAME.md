# Agregar juegos y películas a Coco Launcher 2

El host decide qué se distribuye y el agente prepara, comprueba y publica cuando está autorizado. El host autoriza subir sus archivos a GitHub. Minecraft permanece pospuesto. Lee también `launcher2/AGENTS.md`; no apliques automáticamente las recetas de Coco 1.

## Ruta rápida (léela primero)

**¿Dónde está la lista de juegos y qué la hace aparecer?** La lista es `launcher/catalog.template.json`. `node scripts/sync-catalog.mjs` la convierte en `desktop/src-tauri/resources/catalog.json` (+ manifests) y **compilar** el Setup la incrusta dentro del `.exe`. Por eso un juego añadido al repo **no aparece en ningún Coco instalado** (tampoco en el del anfitrión) hasta publicar un Setup nuevo; el updater de cada PC lo instala solo. Para verlo sin publicar: `npm run tauri dev` desde `launcher2/desktop`. El canal dinámico firmado (`coco2-catalog-channel.json`) **no está publicado** hoy en `coco2-channel`; no lo cuentes como vía de entrega salvo que lo verifiques. Pedir «agrega este juego» ya autoriza publicar el Setup: el alta no está terminada sin él.

Orden mínimo (detalles en cada sección):

1. Workspace en `D:\CocoWork\<id>` y `TEMP/TMP` allí. Mientras se descarga/inspecciona el ZIP, busca en paralelo los medios de Steam (tarjeta completa, abajo).
2. ZIP → **limpia el `OnlineFix.ini`** (quita la línea `1337=`; el punto 6 de Online-Fix explica las 4 capas anti-aviso/navegador ya implementadas) y cualquier `.url` **antes** de calcular hashes y subir.
3. `New-CocoStandaloneCandidate.ps1` (o multipartes) → prerelease del juego con el ZIP final → verificar tamaño/SHA servidos → `Apply-CocoStandaloneDraft.ps1` (dry-run y apply).
4. Entrada en `src-tauri/resources/online-fix.json` (`games.<id>` y `apps.<realAppId>`, `hash1337: ""`), preview, `sync-steam-screenshots.mjs`, `sync-catalog.mjs`.
5. Instalación nativa + primer arranque con las pruebas opt-in (Online-Fix punto 7). Tests de «Validación y entrega».
6. Subir versión, `Build-CocoLauncher2.ps1`, `Publish-Coco2Release.ps1` (sección «Publicar una versión nueva»). Ninguno de los dos exige Git limpio; un árbol con cambios ajenos **no** bloquea la publicación (no los reviertas ni los commitees por tu cuenta).
7. Limpieza y entrega.

### Trampas que ya costaron tiempo

- `powershell -File script.ps1 -RequiredPaths a,b` llega como **un** string con comas. Invoca el script dentro de la sesión: `& .\script.ps1 -RequiredPaths @('a','b')`.
- PowerShell 5.1 `Set-Content/Out-File -Encoding UTF8` escribe BOM y rompe JSON leído por Node. Usa `[IO.File]::WriteAllText($p,$t,(New-Object Text.UTF8Encoding($false)))`.
- `gh release upload tag 'archivo#nombre'` solo cambia la etiqueta, **no** el nombre del asset. Sube un archivo ya llamado así (hardlink `New-Item -ItemType HardLink`) o usa `gh api ... assets?name=<nombre>` (sección películas).
- Un asset publicado no se reemplaza con otros bytes: un cliente con caché fallaría el hash. Corrige con tag/versión de paquete nuevos.
- Al cambiar un ZIP, su SHA aparece en `pack.sha256`, `pack.archives[].sha256` y en los `requiredFiles` que lo citen; regenera con el borrador en vez de buscar/reemplazar a mano.
- Descargas web con navegador del servidor (p. ej. AnkerGames: `Download` → `Direct Download` → página con Turnstile y cuenta atrás que **solo avanza con la pestaña visible**): el archivo queda en `%USERPROFILE%\.t3\userdata\server-browser\downloads\<hash>\<uuid>` aunque el diálogo de guardar se cancele. Muévelo a D: y bórralo de ahí al terminar.
- El diálogo «Steam is not launched» en pruebas aisladas es porque Steam está cerrado; Coco lo inicia antes del juego. No es el aviso de Online-Fix.

## Antes de empezar

- Ejecuta `git status --short`; preserva cambios ajenos. Comprueba procesos de Minecraft, Java, Publisher, Cargo, Rust, NSIS y Coco 2. No publiques con Minecraft, LAN o Publisher abiertos ni compiles dos releases a la vez.
- Identifica fuente, versión, ejecutable y portada sin ejecutar el juego. Comprueba derechos, rutas seguras, enlaces, colisiones Windows, ausencia de secretos y datos personales. No incluyas partidas, `playerdata`, estadísticas ni cachés generadas; nunca borres datos del usuario.
- Reutiliza borradores y hashes vigentes sin sobrescribirlos. No reinstales dependencias ni recompiles para inspeccionar. Mide antes de optimizar y no inventes tiempos.
- Decide el disco de trabajo **antes** de descargar o copiar. Si el anfitrión pide D:, usa allí herramientas portátiles, paquetes, caché de prueba, temporales e instalación (`TEMP`/`TMP` del proceso y ubicación registrada del juego). El código y metadatos pequeños permanecen en el repositorio. No dupliques el juego entero para empaquetarlo ni muevas/borres su fuente sin autorización.
- Trabaja de principio a fin con la autorización ya dada: prepara, valida, integra y publica. Una prueba que requiera otro PC o un perfil limpio se registra como pendiente y no detiene por sí sola la entrega; una falla reproducida sí se corrige o se comunica con precisión. No conviertas dudas rutinarias en otra solicitud de permiso.

## Preparar un standalone

1. Si recibes una carpeta, crea un ZIP con el juego en su raíz y excluye archivos personales. Mide la compresión: puede ahorrar subida y descarga. GitHub limita cada asset de release a menos de 2 GiB. No modifiques la fuente del usuario.
2. Inspecciona con `launcher2/desktop/scripts/Inspect-Coco2AgentGame.ps1 -ZipPath <zip> -Name <nombre>`. El creador de borradores calcula el hash; evita repetirlo. Elige el ejecutable con evidencia. Si falta portada, usa una imagen neutral identificada como provisional.
3. Para un ZIP tradicional, `New-CocoStandaloneCandidate.ps1` crea un borrador inmutable en `launcher2/drafts/<id>/`; también existe `QuickAdd-Coco2Agent.mjs`. Para el inventario del empaquetador multipartes, usa `New-CocoMultipartCandidate.py --inventory <inventory.json> --id <id> --name <nombre> --version <version> --executable <ruta> --description <español> --cover <imagen> [--require <ruta>]`: genera catálogo, lock, portada y revisión **sin volver a leer/descomprimir todos los ZIP**. Una URL propuesta no demuestra que el ZIP esté publicado. Lee `REVIEW.txt` y valida `requiredFiles`, SHA-256, tamaño, runtime, hosting y derechos.
4. Ejecuta `Apply-CocoStandaloneDraft.ps1 -DraftId <id> -SourceZipPath <zip>` en dry-run. Tras revisar derechos, aplica con `-Apply -ApproveReviewedLicenseRights -ExpectedCatalogSha256 <hash>`; nunca reemplaces un draft o catálogo ajeno. Para actualizaciones usa el flujo de update de Host Studio, no un ID duplicado.
5. La fuente es `launcher/catalog.template.json`, con lock en `launcher/experiences/<id>.lock.json` y portada en `assets/experiences/`. Ejecuta `node scripts/sync-catalog.mjs` desde `launcher2/desktop`; no edites sus recursos generados a mano.

**Tarjeta completa en cada alta:** consulta `https://store.steampowered.com/api/appdetails?appids=<SteamAppId>&l=spanish` una sola vez para obtener nombre, descripción, portada y tráileres. Redacta en `description` un resumen breve y natural en español con el género, objetivo y número de jugadores cuando esté verificado; no dejes el texto genérico del borrador. Copia a `assets/experiences/` la cápsula oficial **616×353** (`main_capsule` de `IStoreBrowseService/GetItems` con `include_assets`, o `capsule_616x353.jpg`; si es estacional, `.../apps/<id>/capsule_616x353.jpg` suele dar la base): las tarjetas son 16:9 y el `header` 460×215 pierde los costados y registra el preview de Steam en `desktop/src/game-hover-previews.json`. Prueba primero `https://cdn.akamai.steamstatic.com/steam/apps/<trailerId>/microtrailer.webm`; si no existe, busca un MP4 oficial de Steam o prepara un clip local corto y silencioso del HLS oficial, como `desktop/public/previews/yapyap-steam.mp4`. Comprueba URL o archivo, tamaño, reproducción y procedencia; después ejecuta `node scripts/sync-steam-screenshots.mjs` desde `launcher2/desktop` para la galería del detalle (lee el `steamAppId` del preview), actualiza las pruebas y ejecuta `sync-catalog.mjs`. Haz la búsqueda de medios en paralelo con la inspección del ZIP y evita recompilar hasta reunir todos los cambios. Si no existe una fuente válida, usa portada neutral provisional, documenta el preview pendiente y no inventes medios.

## Evitar avisos promocionales y aperturas de navegador (todos los juegos)

Este procedimiento forma parte de **cada alta o actualización**, aunque el juego no use Online-Fix o no tenga una DLL con ese nombre. Se generaliza la investigación y la validación, **nunca offsets, bytes o hashes de otro juego**. Los hashes de aceptación en un INI y el cierre automático de ventanas no bastan para demostrar prevención: un aviso puede llegar a mostrarse y su botón puede abrir el navegador antes de que el launcher intervenga.

1. **Inventariar sin ejecutar.** Trabaja en una copia o con overrides de empaquetado, conservando la fuente. Identifica arquitectura PE, DLL cargadas, imports normales/diferidos, exports y cadenas ANSI/UTF-16. Revisa también proxies como `version.dll`, `winmm.dll`, componentes anidados y ejecutables auxiliares. Busca tanto APIs de cuadros de diálogo como creación de ventanas propias, recursos/video de créditos, accesos `.url` y lanzadores de enlaces/procesos. No asumas que buscar `MessageBox` o renombrar un import cubre todo.
2. **Localizar la ruta efectiva.** Comprueba llamadas y referencias: una apertura puede usar imports, resolución dinámica `LoadLibrary`/`GetProcAddress`, un hilo auxiliar o una URL generada al arrancar. Identifica entrada, llamadores, argumentos, retorno y limpieza de la rutina promocional, diferenciándola del inicio del juego, Steam, red y partidas. Una cadena o un import aislados señalan una posibilidad; no demuestran por sí solos que esa versión vaya a mostrar algo.
3. **Prevenir en origen y añadir respaldos compatibles.** Cuando hay evidencia suficiente, omite la rutina promocional **antes** de crear ventanas, escribir accesos o lanzar enlaces, conservando el retorno que espera el llamador. Si resuelve dinámicamente una API de navegador, un respaldo puede impedir esa resolución **solo si** el código comprueba el resultado nulo antes de usarlo. En un splash propio, omite su preparación/reproducción mediante la rama existente de «sin video» cuando esa rama conserve flags de finalización, liberación de contexto, hilos y continuación del juego. Elimina accesos promocionales del paquete; si el programa requiere su existencia, prueba una alternativa inerte compatible. No sustituyas APIs de firmas distintas a ciegas, no neutralices indiscriminadamente llamadas del juego ni bloquees navegadores/red de todo Windows.
4. **Respetar arquitectura y ABI.** En x86, el número de argumentos y quién limpia la pila son críticos: `MessageBox` y `MessageBeep` tienen firmas distintas. En x64 tampoco basta con que una sustitución «cargue»: comprueba argumentos, retorno, uso del resultado y registro/pila. No renombres una exportación que otro módulo necesite como punto de entrada. Si no se entiende una ruta o no se conserva su contrato, no la parchees por tanteo; registra qué falta investigar. Los offsets de Party Animals **solo** valen para su DLL exacta y están en [su auditoría](PartyAnimals-1.17.2.0-audit.md).
5. **Hacer reproducible y verificable la preparación.** La receta debe exigir SHA-256 upstream, arquitectura y bytes esperados, rechazar builds desconocidas y producir un informe de cambios/hash final sin alterar el original. Prepara antes de comprimir. Fija los binarios finales relevantes en `runtime.requiredFiles` y vuelve a calcular hashes de cada ZIP, catálogo y lock. Coco debe rechazar un loader distinto del autorizado; no introducir una restauración silenciosa de la DLL original. Para un juego ya publicado, usa una versión de paquete nueva y verifica actualización/reparación de la instalación: publicar B no demuestra que todas las instalaciones A ya tengan los bytes corregidos.
6. **Online-Fix: Coco ya trae la protección; el agente solo la alimenta y la prueba.** No reimplementes nada ni parchees binarios por esto. Al pulsar Jugar, Coco 2 (`services/standalone.rs`, `launch_standalone`) hace en este orden:
   1. **Hash recordado** (`game_prepare.rs`, `prepare_online_fix`): borra `OnlineFix.url`, completa `0` desde `online-fix.json` y, si este PC ya conoce su `1337` para esa carpeta (`%LOCALAPPDATA%\CocoMinecraftUpdater\online-fix-trust.json`, por equipo+carpeta+DLL del fix), lo escribe. Con hash válido el fix no muestra nada.
   2. **Primer arranque invisible** (`online_fix_prime.rs`), solo si ese PC aún no conoce el hash: abre el juego en un **escritorio oculto** dentro de un Job Object que permite **un solo proceso** (Windows impide cualquier navegador) y lo mata en cuanto el fix escribe el `1337` de ese PC, antes de que pida el aviso. Guarda el valor como confianza local. Es el mecanismo **principal**; se repite en otro PC, otra carpeta o si cambia la DLL del fix.
   3. **Detector de avisos** (`launch_guard.rs`, `guard_credits_box` durante 10 min, más el escaneo cada 200 ms de `watch_popups`): un gancho `EVENT_OBJECT_SHOW` oculta y responde el aviso firmado por `online-fix.me`. Es un **respaldo**: actúa al mostrarse, así que puede verse un destello.
   4. **Matar navegadores** (`guard_children`): el juego nace suspendido dentro de un Job Object sin límites y cada proceso nuevo que sea navegador (lista + los registrados en el PC, p. ej. Zen) o `explorer.exe`/`LaunchWinApp`/`OpenWith` muere al nacer. Log: `%LOCALAPPDATA%\CocoMinecraftUpdater\logs`, etiqueta `[online-fix]`.

   **Qué hace el agente por juego:**
   - Añade `games.<id>` y `apps.<RealAppId>` en `desktop/src-tauri/resources/online-fix.json` con `realAppId`, `hash0` (el `0=` del INI) y `hash1337: ""`. Nunca copies un `1337`: está ligado al PC (el del anfitrión no sirvió en el PC de una amiga con CRACK).
   - En el ZIP, quita la línea `1337=` del INI (trae el de quien empaquetó). `""` en la tabla **no la borra** (`with_hashes` conserva la existente). Conserva `0`, `1` y demás claves; no inventes INI para otros loaders. La verificación previa solo exige que `OnlineFix.ini` exista.
   - El paso 2 usa la carpeta donde vive el fix (junto a `OnlineFix64.dll`/`OnlineFix.dll`, o su INI si va dentro de otra DLL) y arranca el programa que lo carga (`-Shipping.exe` de Unreal, `love.exe`…). En Unreal el fix puede estar en `Engine/Binaries/ThirdParty/Steamworks/...`; sin ejecutable allí, Coco usa el `-Shipping.exe` del catálogo. No elijas como ejecutable un bootstrapper que crea otro proceso: el paso 2 permite solo uno.
   - **Prueba el camino principal**, no solo el respaldo: sobre una copia instalada con el `1337` ausente o inválido, `COCO_PRIME_ROOT=<carpeta> COCO_PRIME_EXE=<exe relativo> cargo test --lib real_first_run -- --ignored --nocapture`. Éxito = `conclusive true`, hashes cambiados, `credits box on screen afterwards: false` y en el log `hash_written: true, popup_answered: false`. `COCO_PRIME_ID=<id>` registra además la confianza de este PC; no distribuyas ese estado.
   - La prueba del punto 7 (`a_rejected_hash_shows_no_box_and_opens_no_page`) **se salta el paso 2** y fuerza el peor caso: un destello del aviso y `navegador ... cerrado al nacer` en el log son el respaldo funcionando, no un fallo del paquete. Referencias: CRACK, YAPYAP, Heavenly Bodies (x86), Pilgrim, Golf It, Move or Die y Buckshot Roulette escribieron el hash en el paso 2 sin aviso.
7. **Probar instalación y primer arranque reales.** Instala los ZIP finales mediante el instalador nativo. Antes de abrir, avisa al anfitrión. Usa un perfil de prueba aislado sin aceptación anterior, o una ubicación de estado nueva que el componente efectivamente utilice; cambiar variables de entorno no garantiza aislar todas las rutas de Windows. **Nunca borres estado, partidas o preferencias existentes para simularlo.** Observa aviso y navegador, confirma continuación del juego y repite el arranque. Registra observación visual del anfitrión o captura disponible, estado inicial y límites. Un monitor de procesos no disponible, una lista vacía sin monitor activo, ausencia de `.url` o llegar al menú no sustituyen la observación ni validan multijugador.
   Prueba visible protegida: `COCO_GUARD_ROOT=<carpeta>`, `COCO_GUARD_EXE=<ruta relativa>`, `COCO_GUARD_SECONDS=75`, `COCO_GUARD_REQUIRE_RUNNING=1` y opcionalmente `COCO_GUARD_ARGS` como array JSON de argumentos; ejecuta `cargo test --lib a_rejected_hash_shows_no_box_and_opens_no_page -- --ignored --nocapture --test-threads=1`. Usa el guard de producción y termina únicamente su proceso de prueba al finalizar. El nombre histórico del test no modifica por sí solo el INI: documenta si se probó aceptación válida o rechazada. El escaneo sin avisos y el proceso vivo son evidencia instrumental, no observación visual ni prueba de otro PC.
8. **Cerrar la evidencia por versión.** Distingue «rutas aún presentes», «aceptación INI local», «prevención binaria preparada», «primer arranque probado» y «validado en otro PC». Conserva resultados y hashes en la auditoría del juego. No extrapoles un éxito a otras versiones, equipos o juegos ni prometas ausencia de cualquier ventana de Steam/Windows/error. Si falla una prueba reproducible, corrige o comunica el bloqueo antes de afirmar que está resuelto.

Ejemplo verificado por el anfitrión: Party Animals 1.17.2.0 no importaba MessageBox; creaba su acceso y abría el navegador desde un hilo con resolución dinámica, además de un splash propio. Omitir el hilo, impedir su resolución de navegador con comprobación nula y tomar la rama sin splash evitó aviso y página en la prueba observada. Es una referencia del método, no una receta de bytes para otros títulos.

## Juegos grandes y partes

**Descarga e instalación tienen tamaños distintos.** Un RAR de 6 GB puede contener 16 GB de juego completo; compara rutas/tamaños y mide antes de asumir que faltan archivos. Un RAR cifrado requiere la clave del anfitrión: no la imprimas ni la guardes en scripts, catálogo o paquetes. El instalador de Coco consume **ZIP**, no RAR: no basta con renombrarlo, partir el RAR o meterlo en un ZIP. Se empaquetan los archivos preparados en el formato nativo compatible.

Para preparar partes sin una copia completa ni trozos temporales, usa `desktop/scripts/New-CocoMultipartArchives.py <fuente> <salida> --prefix <nombre-version> --base-url <release-https>`. Opciones:

- `--split-large`: un archivo mayor de 1.800.000.000 bytes se lee por rangos y entra como `archivo.part1`, `.part2`, etc. en ZIP independientes. El instalador los reconstruye en staging. No son volúmenes `.z01` ni ZIP partidos. El inventario registra también SHA-256/tamaño del archivo reconstruido. Se rechazan colisiones con nombres reales. Sin esta opción, un archivo demasiado grande se rechaza.
- `--compression deflate --level 1` (predeterminado), `--compression store` o `--compression zstd --level 9`. Mide una muestra de varios lugares del archivo grande: algunos bundles ya están comprimidos y recomprimirlos apenas ahorra, mientras otros UCAS de Unreal sí reducen mucho. Zstandard ya está habilitado en el ZIP nativo de Coco; Python necesita **3.14+**. Prueba pequeña verificada: ZIP método 93 escrito por Python 3.14 mediante streaming/ZIP64 y extraído por el instalador Rust (`python314_streamed_zstandard_zip_uses_the_native_installer`). No uses el creador PowerShell de un solo ZIP para descomprimir Zstandard: usa el inventario y el creador multipartes.
- `--jobs 2` comprime dos ZIP a la vez; máximo 4, sin multiplicar copias del juego. No elijas más procesos solo por el número de núcleos: también importan RAM y disco.
- `--override ruta/relativa=archivo-preparado` reemplaza únicamente esos bytes al empaquetar, conservando la fuente. `--exclude <ruta exacta>` omite accesos promocionales o personales revisados; un `.url` o `.lnk` no excluido provoca rechazo. No empaquetes enlaces a partidas, estado de usuario ni claves.
- `--resume` verifica y reutiliza partes completas y reconstruye el ZIP truncado de una interrupción. No sobrescribe una parte válida con otros bytes. Revisa `inventory.json` antes de crear el borrador.

Si falta Python 3.14, reutiliza o prepara una copia **portátil en D:** desde el ZIP embebible oficial de `python.org`, verifica la firma Authenticode de `python.exe` (Python Software Foundation, estado Valid) y registra versión/procedencia. No cambies el Python global ni reinstales dependencias del launcher para empaquetar. El Python 3.13 existente sigue sirviendo para Deflate y Store.

Ejemplo del flujo rápido, con un ejecutable ya elegido y una portada oficial ya descargada:

```powershell
$env:TEMP = 'D:\CocoWork\mi-juego\temp'
$env:TMP = $env:TEMP
New-Item -ItemType Directory -Path $env:TEMP -Force | Out-Null
& 'D:\CocoWork\tools\python-3.14.0\python.exe' launcher2/desktop/scripts/New-CocoMultipartArchives.py '<fuente>' 'D:\CocoWork\mi-juego\archives' --prefix mi-juego-1.0 --base-url 'https://github.com/<owner>/<repo>/releases/download/<tag>' --split-large --compression zstd --level 9 --jobs 2
python launcher2/desktop/scripts/New-CocoMultipartCandidate.py --inventory 'D:\CocoWork\mi-juego\archives\inventory.json' --id mi-juego --name 'Mi juego' --version 1.0 --executable 'Game/Binaries/Win64/Game-Win64-Shipping.exe' --description 'Descripción revisada en español.' --cover 'D:\CocoWork\mi-juego\cover.jpg'
```

`Apply-CocoStandaloneDraft.ps1 -SourceZipDirectory <carpeta>` valida **todas** las partes locales y su lock antes de promocionar. Tras un dry-run que ya leyó sus hashes, aplica el mismo borrador con el SHA del catálogo revisado; no vuelvas a leer innecesariamente todos los GB si los bytes no cambiaron. El lock conserva `archive` como primera parte y añade `archives` en orden; `pack.size` es la suma descargable. Esto no modifica el sellado de Host Studio ni publica un canal remoto.

Comprueba el SHA-256 del UCAS u otro archivo grande **una vez después de reconstruirlo**, contra `reassembledFiles` del inventario. No lo añadas a `requiredFiles` solo para repetir decenas de GB de hash antes de cada partida: los ZIP ya se verifican completos durante la instalación y `requiredFiles` debe cubrir ejecutables, loaders y componentes/índices esenciales. Al estimar espacio libre cuenta **ZIP + staging descomprimido + la copia temporal del mayor archivo reconstruido**, no solo la descarga. Para validar sin una segunda instalación, la prueba opt-in `host_package_install_smoke` acepta `COCO2_HOST_SMOKE_ID`, `COCO2_HOST_SMOKE_TARGET` y `COCO2_HOST_SMOKE_CACHE`: destino nuevo y caché precargada en D:, sin tocar instalaciones existentes. El resultado queda instalado para el anfitrión. Mide extracción y reconstrucción: esta última todavía copia las piezas al archivo final antes de eliminarlas, añade E/S y puede dominar la instalación en un disco lento. No confundir un empaquetado rápido con una instalación igual de rápida; no repetir una instalación completa si basta verificar el hash reconstruido.

El instalador admite varios ZIP independientes, cada uno con URL, tamaño y SHA-256, y reconstruye archivos internos `.part1`, `.part2`, etc. Los ZIP deben tener rutas compatibles sin colisiones; verifica cada parte y los archivos reconstruidos. `pack.archives` del catálogo embebido puede incluirlas. El empaquetador y sellado de Host Studio todavía trabajan con un solo ZIP: no declares listo un flujo dinámico multipartes hasta implementar y probar sellado, revisión, firma, subida y verificación de **todas** las partes. Las versiones antiguas del cliente también deben actualizarse para aceptar un catálogo remoto multipartes. Una importación local sin firma nunca autoriza un juego nuevo.

## Agregar películas y series

1. Localiza el archivo real y conserva el original. Usa `ffprobe -v error -show_streams -show_format -of json <archivo>` para registrar duración, resolución, códec, profundidad de bits, audio y subtítulos. Un MP4 no implica H.264: HEVC/H.265 y Main 10 pueden sonar sin imagen en WebView2 según Windows/GPU. Coco reproduce las películas con libVLC embebido y decodificadores propios: **no recodifiques el vídeo por defecto** ni pidas instalar códecs del sistema. Verifica decodificación por software del original con el runtime fijado, además del render y controles integrados.
2. Identifica título/año y redacta una reseña breve en español, sin spoilers, con premisa y tono. Usa sinopsis oficial y portada oficial horizontal cuando exista; registra procedencia. `description` no contiene instrucciones de reproducción/descarga, rutas Downloads ni texto de plantilla. No anuncies subtítulos españoles si no están comprobados: un `.srt` junto al vídeo no se incorpora automáticamente. Si se solicitan subtítulos, prepara una pista compatible y su integración explícita; no cambies el vídeo a escondidas.
3. Publica el **archivo original** en un prerelease propio, nunca Latest. Cada asset debe pesar menos de 2 GiB. Un ZIP o RAR no sirve como URL de streaming. Si supera el límite, hace falta un mecanismo de distribución compatible aprobado; no declares listo un MP4 partido ni lo recodifiques sin acordar esa alternativa. Usa una URL/nombre estables e inmutables y calcula tamaño/SHA-256 de los bytes realmente publicados. Con `gh api --method POST https://uploads.github.com/repos/<owner>/<repo>/releases/<releaseId>/assets?name=<nombre> --input <archivo> -H "Content-Type: video/mp4"` se puede subir el original con un nombre de asset limpio sin crear una copia completa solo para renombrarlo.
4. Añade entrada en `launcher/catalog.template.json`: `runtime.type: "media"`, `launch.workflow: "coco-media"`, `content.type: "movie"` o `"episodic-video"`. Cada episodio declara `id`, `title`, `fileName`, `sourceUrl`, `streamUrl`, `size`, `sha256`. Para películas conserva `content.movie` y `content.episodes[0]` idénticos mientras ambos contratos existan; para series usa IDs únicos y orden de capítulos correcto. No se crea un lock de juego ni un ZIP de instalación. Portada en `assets/experiences/` mediante `ui.imagePath`.
5. Ejecuta `sync-catalog.mjs`: genera el catálogo público sin URLs privadas y `src-tauri/resources/media-manifests.json` para el backend. Actualiza pruebas de catálogo si corresponde, valida hashes/digests del servidor y HTTP Range público (206, tamaño Content-Range y bytes reales). La UI ya no ofrece descargar películas; conserva solo la compatibilidad con archivos locales verificados existentes.
6. Prueba el original con el motor empaquetado, incluyendo HEVC/Main 10 por software, reproducción y audio, pausa/reanudación, saltos, volumen, fullscreen, resize/DPI y cierre/reapertura sin audio huérfano. El decoder entrega RGBA mediante SharedBuffer de WebView2 y el frontend dibuja un canvas **en el mismo compositor DOM que los controles**. No uses un HWND hijo, máscaras Win32 ni espacio reservado para barras. Encaja el fotograma completo en toda la ventana con `min(anchoDisponible/anchoVideo, altoDisponible/altoVideo)`: toca el primer borde, conserva proporción y no cambia de tamaño al mostrar controles. Las franjas restantes por diferencia de proporción son normales; no uses zoom ni estiramiento para quitarlas. Verifica ambos renglones de subtítulos incrustados y que el reloj al pasar sobre la barra quede encima del vídeo, también en pausa y fullscreen. Usa dimensiones **visibles** y SAR de la pista, no alto codificado/alineado (p. ej. 804, no 832). No confundas un fotograma del SDK con comprobar todo el recorrido WebView2/canvas/controles. Registra por separado evidencia del host y prueba pendiente en otro PC. El menú contextual y las etiquetas técnicas de contenedor no forman parte del visor.
7. Un cambio del catálogo embebido requiere nueva versión del Setup por el flujo habitual. No reemplaces el vídeo ya publicado para corregir el reproductor: conserva sus bytes. `Get-Coco2PlayerRuntime.ps1` obtiene VLC desde VideoLAN, verifica archivo y cada fichero con `resources/vlc-runtime-manifest.json` y reutiliza caché en D:. El builder empaqueta únicamente esos archivos y avisos/licencias; la extracción NSIS final coteja todos sus hashes. No instala asociaciones ni códecs de Windows. Limpia temporales propios al cerrar la tarea.

Para desarrollar el visor sin compilar un release, prepara el runtime una vez y pásalo solo al proceso de desarrollo: `$env:COCO_PLAYER_RUNTIME = & .\scripts\Get-Coco2PlayerRuntime.ps1`, después `npm run tauri dev` desde `launcher2/desktop`. Esa variable solo se admite en debug; el producto instalado usa sus recursos empaquetados. La prueba opt-in `real_vlc_hevc_frames_and_controls` acepta `COCO_PLAYER_RUNTIME`, `COCO_PLAYER_SMOKE_SOURCE` (archivo original o stream de prueba) y `COCO_PLAYER_SMOKE_FRAME` (archivo RGBA nuevo en D:, con dimensiones/stride en su `.json`); decodifica por software, silencia audio y cierra al terminar. Las pruebas de `native-playback.test.mjs` cubren copia completa del fotograma, contain y ciclo de vida. Documenta por separado la comprobación visual integrada que no se haya observado.

## Distribución autorizada

- **Catálogo embebido:** integra fuente y recursos, sube cada ZIP a un prerelease propio del juego (no Latest), verifica tamaño y SHA servidos y publica un Setup nuevo firmado. Incrementa la misma versión en `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock`, `tauri.conf.json` y `tests/version-contract-v12.test.mjs`. Para probar cambios de interfaz usa `npm run tauri dev` (recarga al guardar) y compila el instalador solo al publicar. Compila una vez con `desktop/scripts/Build-CocoLauncher2.ps1` (Cargo en PATH; con cualquier 7-Zip se revisa además el instalador, y lo que esa versión no pueda leer se omite); publica el candidato con `Publish-Coco2Release.ps1`. El updater usa `coco2-channel/latest.json`, no `releases/latest` de Coco 1.
- **Canal dinámico:** el cliente consulta `coco2-catalog-channel.json` y su firma Ed25519 en `coco2-channel` al abrir, cada 15 minutos y al recuperar el foco. Un artefacto de Host Studio sin firma es solo borrador. Sella, revisa y firma los bytes exactos con la clave del host; comprueba procedencia, secuencia, todas las URLs y hashes antes de publicar. No expongas la clave. Un catálogo firmado actualizado puede agregar juegos sin recompilar cuando la versión instalada soporta su formato.

### Publicar una versión nueva

Desde `launcher2/desktop`, sin otro Cargo/build activo:

1. Sube el parche (p. ej. 0.6.50 → 0.6.51) en `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json` y `tests/version-contract-v12.test.mjs`. Nunca reutilices una versión ya publicada.
2. `sync-catalog.mjs` y las pruebas de la alta deben estar en verde.
3. `.\scripts\Build-CocoLauncher2.ps1`: compila, firma y deja el candidato en `launcher2/dist/publish-ready/<versión>-<sha12>/` (no en `desktop/dist`) (Setup, `.sig`, `latest.json`). Si se cortó tras compilar, `-FinalizeExisting`.
4. `.\scripts\Publish-Coco2Release.ps1 -CandidatePath <esa carpeta>`: sube a `coco2-channel`, descarga lo servido y compara; falla si `coco2-channel` quedara como Latest.
5. Registra versión, tamaño y SHA en `launcher2/README.md`. El Coco instalado del anfitrión se actualiza solo al abrirlo (o reinstala silencioso con el Setup); confirma que el juego aparece.

La publicación exige autorización del host; no afirmes disponibilidad hasta verificar lo servido. El Setup compartible está en `https://github.com/Franco-Caballero/CocoMinecraftUpdater/releases/download/coco2-channel/CocoLauncher2-Setup.exe`. Un `.coco2pack` local sin firma no incorpora juegos al catálogo de amigos.

## Validación y entrega

### Limpieza al terminar

Las copias `runtime-test`, `prepared-check` y los ZIP de `release-upload` son temporales del agente, no instalaciones del jugador. No deben quedar acumulados en `%TEMP%`. Usa un workspace propio en D: para tareas pesadas y registra sus rutas al crearlas. En scripts, libera los temporales propios en `finally`, también si falla la prueba o subida; conserva únicamente logs pequeños necesarios para diagnosticar una falla. Evita extraer una copia completa si la instalación nativa de prueba ya sirve para validar el juego.

Tras verificar publicación, tamaños y hashes remotos, elimina los ZIP locales de subida y las copias de prueba que ya no se usan. Antes de borrar verifica rutas absolutas, ausencia de enlaces/reparse y procesos activos; nunca deduzcas que cualquier carpeta llamada `coco*` es desechable. Conserva juego instalado, partidas, fuentes del usuario salvo autorización de borrado, claves de firma, catálogo, locks, medios y auditorías. Si la sesión se interrumpe, la siguiente tarea debe inventariar y cerrar su workspace pendiente.

Las cachés Rust `target/*/incremental` son regenerables. Por preferencia del anfitrión de limitar crecimiento, los perfiles dev y release desactivan incremental: conservan dependencias compiladas, pero recompilar el código de Coco puede tardar más. Las cachés antiguas no desaparecen por cambiar ese ajuste; con autorización de limpieza y sin Cargo/Rust activos se pueden retirar. No borres todas las dependencias automáticamente. El builder usa un workspace único en `D:\CocoWork\build-temp` cuando D: existe (TEMP en otros equipos), restaura el entorno y limpia solo ese workspace en `finally`, también ante fallos; avisa si no pudo limpiarlo. No limpia carpetas antiguas ajenas a su invocación ni puede garantizar limpieza tras terminar forzosamente el proceso. Informa espacio realmente recuperado, no solo tamaño lógico de archivos con hardlinks.

Para cada alta: JSON, PowerShell, `tests/Test-CocoLauncherCatalog.ps1`, `tests/Test-CocoLauncherLaunch.ps1`, `git diff --check`, `sync-catalog.mjs`, pruebas Node de catálogo y `npx tsc --noEmit`. Si cambia instalación, archivos o aislamiento, incluye pruebas de instancia e integración; si cambia el instalador, añade pruebas Rust. Para un release usa el builder y su preflight. Comprueba descarga y hash remoto, instalación reanudable y arranque real; prueba host y cliente cuando afecte red. Conserva mundos y partidas. Señala las pruebas pendientes.

Entrega ID, versión, ZIP o partes y hashes, ejecutable, portada, cambios y pruebas; distingue **borrador**, **catálogo integrado**, **canal firmado publicado** y **Setup publicado y verificado**. El estado publicado y la evidencia extensa van en `launcher2/README.md` o una auditoría, no en esta guía.
